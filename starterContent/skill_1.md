# Evis UI — Interface Behavior & Integration Skill

## Purpose

This skill is responsible for designing, auditing, correcting, and extending the user interface of **Evis**, a modular local AI workspace.

Evis is a desktop-oriented AI workspace designed primarily for Linux.

The interface must provide a modern AI workspace experience while remaining modular, flexible, provider-independent, and dynamically connected to the capabilities actually available on the user's system.

This skill does NOT define the entire Evis architecture.

It defines the **UI behavior, interaction model, dynamic integrations, feature surfaces, and rules required to make the interface behave like a real application rather than a static mockup.**

---

# 1. Fundamental Rule

The UI must represent the **real state of the system**.

Never invent:

* AI models
* installed providers
* installed skills
* exercises
* projects
* files
* tools
* integrations
* permissions
* capabilities

If something does not exist or cannot currently be detected, the UI must not present it as active or installed.

Use states such as:

```text
Available
Installed
Active
Inactive
Unavailable
Not configured
Not detected
```

Never silently convert a placeholder into a real capability.

---

# 2. Evis Identity

The application name is:

```text
Evis
```

Do not use:

```text
New Agent Assistance
AI Assistant
Local AI Assistant
New Agent
```

as the primary application name.

The interface should consistently use **Evis**.

---

# 3. Core UI Philosophy

Evis should feel like one coherent application.

The user should not have to think about:

* containers
* backend processes
* API endpoints
* ports
* provider implementation details
* React components
* service wiring
* internal databases

unless they intentionally open an advanced configuration area.

The UI is the abstraction layer between the user and the underlying system.

---

# 4. Modern Interaction Requirements

The interface must provide normal modern application behaviors.

These behaviors are not optional visual decorations.

They are part of the interaction system.

Required behaviors include:

* selection
* text selection
* keyboard navigation
* copy
* paste
* cut
* contextual actions
* hover states
* focus states
* active states
* disabled states
* loading states
* error states
* success states
* empty states
* tooltips
* expandable sections
* collapsible panels
* resizable panels where appropriate
* drag-and-drop where appropriate
* keyboard shortcuts
* message actions
* search interactions
* model selection
* skill selection
* file selection

The interface must behave like an application, not like a collection of static cards.

---

# 5. Text and Code Copying

AI responses frequently contain:

* normal text
* code
* commands
* paths
* configuration
* JSON
* Markdown

The interface must automatically provide copying functionality where appropriate.

For example:

```text
┌──────────────────────────────┐
│ const user = new User();     │
│                              │
│                         Copy │
└──────────────────────────────┘
```

Copy controls should be generated by the message/code rendering system.

Do not manually add a copy button separately to every code block.

The renderer should automatically identify copyable content.

After copying:

```text
Copy
  ↓
Copied
  ↓
Copy
```

The feedback must be temporary and non-disruptive.

Copying must not:

* open a new page
* interrupt the conversation
* replace the current view
* display a blocking dialog

---

# 6. Conversation Interaction

The conversation is the primary workspace.

Users must be able to:

* send messages
* edit their own messages
* copy messages
* copy code blocks
* select text
* scroll naturally
* continue the conversation
* attach files
* activate skills
* select models
* use voice input
* listen to AI responses
* search conversation content
* archive the conversation

Actions must occur inline whenever possible.

Avoid blocking dialogs for ordinary interactions.

---

# 7. Voice Input

The message composer must reserve an interface control for voice input.

Example:

```text
┌───────────────────────────────────────────────┐
│ Message...                              🎤  ↑ │
└───────────────────────────────────────────────┘
```

Voice input should eventually support:

```text
Idle
 ↓
Listening
 ↓
Transcribing
 ↓
Text inserted into composer
 ↓
User reviews
 ↓
Send
```

Do not automatically send transcribed speech unless explicitly configured.

The UI must clearly indicate when the microphone is active.

---

# 8. Text-to-Speech

AI messages should support optional text-to-speech.

Each appropriate assistant message should expose an action such as:

```text
Copy
Read aloud
Stop
```

The speech system must operate independently of the AI model.

The model produces text.

The speech system consumes the text.

Architecture:

```text
AI Response
     ↓
Message Renderer
     ↓
Text-to-Speech Service
     ↓
Audio Output
```

The UI must allow playback to start and stop.

---

# 9. Skill Hub

The Skill Hub is responsible for discovering and managing installed skills.

The Skill Hub must distinguish:

```text
Installed Skills
Available Skills
Active Skills
Disabled Skills
Unavailable Skills
```

Example:

```text
Skills

Installed
──────────────
JavaScript Tutor
File Explorer
Knowledge Vault

Available
──────────────
Web Search
Terminal
```

The Skill Hub must not automatically create skills unless explicitly instructed.

---

# 10. Active Skills

The current conversation/session should expose its active skills.

The active skills should already be represented near the message composer.

Example:

```text
[ JavaScript Tutor ] [ Knowledge ] [ Files ]
```

Do NOT duplicate the same skill list at the top of the conversation merely for decoration.

If active skills are already visible near the composer, the conversation header should remain minimal.

Avoid:

```text
JavaScript Tutor
Knowledge Vault
File Explorer
Current Skills
Active Skills
...
```

all appearing simultaneously.

Information must not be duplicated without a functional reason.

---

# 11. Skill Activation

Skills are activated based on the current task.

The user may explicitly activate a skill.

Example:

```text
Today I want to work on JavaScript classes.

[+]
→ Skills
   ✓ JavaScript Tutor
```

The skill becomes part of the current session context.

The system must not permanently activate every installed skill.

Only the necessary skills should be active.

---

# 12. Exercise Skill

Exercises are NOT global UI content that the system should invent automatically.

The Exercise system must only create exercise sections when explicitly requested.

Example:

```text
User:
Create an exercise section for JavaScript classes.
```

Only then should the system create or activate the corresponding exercise structure.

The exercise system should have its own dedicated skill.

Conceptually:

```text
Exercise Skill
├── learning objective
├── current level
├── difficulty progression
├── constraints
├── exercise generation rules
├── hint rules
├── validation rules
├── solution rules
└── progression tracking
```

The skill determines how exercises should behave.

The skill does NOT automatically create arbitrary exercises merely because the application has an exercise section.

---

# 13. Exercise Skill Behavior

The exercise skill must distinguish:

```text
Exercise requested
Exercise generated
Exercise active
Exercise completed
Exercise failed
Exercise abandoned
Exercise archived
```

The AI must not skip directly from:

```text
concept
```

to:

```text
complete solution
```

unless the user explicitly asks for the solution.

Default learning behavior:

```text
Problem
   ↓
User attempt
   ↓
Evaluation
   ↓
Hint
   ↓
Retry
   ↓
Explanation
   ↓
Retry
   ↓
Solution if necessary
```

---

# 14. File Explorer

The File Explorer must be a real file-management interface.

It must NOT open a conversation when the user clicks:

```text
File Explorer
```

It must open the file explorer workspace.

The initial view should expose a defined root.

Example:

```text
File Explorer
────────────────────────

Workspace Root
├── projects/
├── knowledge/
├── conversations/
├── skills/
└── ...
```

The exact physical root must be determined by the application configuration.

Do not invent filesystem paths.

---

# 15. File System Entry Point

The application must define a clear filesystem entry point.

Conceptually:

```text
Evis Data Root
│
├── conversations/
├── knowledge/
├── projects/
├── skills/
├── exercises/
├── settings/
└── cache/
```

The actual path must be resolved by the application.

The UI should expose the logical structure without requiring the user to understand the physical implementation.

---

# 16. File Lifecycle

The system must define when data is created.

For example:

### New conversation

```text
New Conversation
      ↓
Conversation ID
      ↓
Conversation storage created
```

### New project

```text
New Project
      ↓
Project directory created
      ↓
Project metadata created
```

### Archive conversation

```text
Conversation
      ↓
Analyze
      ↓
Extract relevant information
      ↓
Create summary / knowledge
      ↓
Mark archived
```

### New skill

```text
Install Skill
      ↓
Validate metadata
      ↓
Validate dependencies
      ↓
Register Skill
      ↓
Available in Skill Hub
```

The UI must reflect these real lifecycle states.

---

# 17. Knowledge Vault

Knowledge Vault is a persistent knowledge interface.

It must allow the user to inspect information extracted from:

* conversations
* projects
* documents
* learning sessions
* manually created notes

Knowledge must be distinguishable from raw conversation history.

Example:

```text
Knowledge Vault

JavaScript
├── Classes
├── DOM
├── Events
└── Arrays

Evis Architecture
├── Skills
├── Memory
├── Model Providers
└── File System
```

The Knowledge Vault must not automatically become a conversation.

It is a knowledge-management surface.

---

# 18. Model Provider Architecture

The UI must NOT hard-code models.

Providers are separate from models.

Current providers include:

```text
Ollama
llama.cpp
```

The UI must discover available providers dynamically.

Conceptually:

```text
Model Provider
      ↓
Detect provider
      ↓
Retrieve installed models
      ↓
Display models
```

---

# 19. Ollama

Ollama must be treated as a provider.

The UI should detect whether Ollama is available.

If available:

```text
Ollama
├── Model A
├── Model B
└── Model C
```

Only models actually detected from Ollama should be displayed as installed.

Do not hard-code model names.

If Ollama has no models:

```text
Ollama
No models detected.
```

---

# 20. llama.cpp

llama.cpp must be treated as another provider.

It must not be merged conceptually with Ollama.

The architecture should allow:

```text
Provider
├── Ollama
│   └── detected models
│
└── llama.cpp
    └── configured/detected models
```

The exact mechanism used to discover llama.cpp models must be defined by its provider adapter.

---

# 21. Model Selection

The user chooses the active provider/model.

Example:

```text
Model

Ollama
  qwen...
  llama...
  ...

llama.cpp
  configured model...
```

When the user changes provider:

```text
Ollama
     ↓
llama.cpp
```

the available model list must update dynamically.

The interface must never display models belonging to the previously selected provider as if they belonged to the new provider.

---

# 22. Default Model

The user must be able to define a default model.

Example:

```text
Set as default
```

The default must be stored in application configuration.

Changing the default must not modify or uninstall models.

The user must remain in control of provider and model selection.

---

# 23. Model Lifecycle

The UI must account for real model lifecycle changes.

The user may:

* install a model
* uninstall a model
* change providers
* change default model
* start/stop a provider
* change configuration

The interface must be able to refresh provider/model state.

Do not assume that the list of models is static.

---

# 24. Search

Search must be non-blocking.

When the user enters a search query:

```text
Search input
     ↓
Search
     ↓
Results update
```

The current workspace should remain visible.

Do NOT:

```text
Search
 ↓
Open blocking alert/dialog
 ↓
Hide conversation
 ↓
Show result
```

unless the user explicitly requested a modal search experience.

Search should behave like a modern application search field.

---

# 25. Search Scope

Search may eventually cover:

```text
Conversations
Projects
Knowledge
Files
Skills
Exercises
```

The interface should make the current search scope clear.

Search results should provide direct navigation to the relevant resource.

---

# 26. No Decorative Features

Every visible UI element must have a purpose.

Do not add:

* fake model names
* fake statistics
* fake exercises
* fake projects
* fake skills
* fake status indicators
* decorative controls pretending to work

If a feature is not implemented:

```text
Not configured
Coming later
Unavailable
```

should be used where appropriate.

A smaller working interface is preferable to a large simulated interface.

---

# 27. React

React may be used as the UI implementation technology.

React is NOT the architecture.

The application must remain understandable at the level of:

```text
components
state
services
interfaces
events
data flow
```

Do not hide application behavior inside unnecessary component-specific logic.

External services should be accessed through dedicated application/service interfaces.

---

# 28. UI and Backend Separation

The UI must not directly hard-code provider behavior.

Bad:

```text
React component
    ↓
hard-coded Ollama request
```

Preferred:

```text
React UI
    ↓
Application Model Service
    ↓
Provider Adapter
    ↓
Ollama / llama.cpp
```

The same principle applies to:

* memory
* files
* skills
* Web
* terminal
* speech
* voice input

---

# 29. Feature Registry

Features should have a defined state.

Conceptually:

```text
Feature
├── id
├── name
├── status
├── availability
├── dependencies
├── permissions
└── UI surface
```

Possible states:

```text
available
active
inactive
unavailable
not_configured
error
```

The interface should derive its state from the feature registry rather than manually duplicating feature state.

---

# 30. Tool and Skill Availability

A skill may require tools.

Example:

```text
JavaScript Tutor
├── Local AI       required
├── Memory         required
├── File System    optional
└── Web Search     optional
```

If a required dependency is unavailable:

```text
JavaScript Tutor
⚠ Dependency unavailable
```

Do not pretend the skill is fully operational.

---

# 31. Interface Behavior Over Appearance

When implementing or correcting the interface, prioritize:

1. behavior
2. state
3. data flow
4. interaction
5. accessibility
6. visual consistency
7. aesthetics

A beautiful button that does nothing is considered incomplete.

---

# 32. Non-Blocking Interaction

Normal UI actions must not interrupt the user's workspace.

Avoid unnecessary:

* browser alerts
* blocking dialogs
* full-screen overlays
* navigation away from the current conversation

Prefer:

* inline messages
* toast notifications
* contextual status
* expandable panels
* non-blocking dropdowns

Blocking confirmation should be reserved for operations where confirmation is genuinely necessary.

---

# 33. Responsive Panels

Panels should behave naturally when resized.

Examples:

```text
Sidebar
Conversation
Context Panel
File Explorer
Terminal
```

Panels may be:

* collapsible
* resizable
* detachable later

The main conversation should preserve usable space.

---

# 34. Contextual Panels

Not every capability needs its own permanent page.

Some capabilities should open contextually.

Examples:

```text
Skill selector
Model selector
Tool selector
File attachment
Conversation search
Message actions
```

The UI should avoid filling the main workspace with unnecessary permanent sections.

---

# 36. What Must NOT Be Done Automatically

The agent implementing this skill must NOT:

* invent installed models
* install models without permission
* select a provider without user choice unless a stored default exists
* create exercises without a request
* create skills without a request
* activate every available skill
* fabricate filesystem data
* fabricate projects
* fabricate knowledge
* fabricate tool availability
* create fake integrations
* replace existing architecture without justification
* rewrite the entire application merely because React is being used
* introduce external APIs unnecessarily
* introduce paid services without explicit architectural justification

---

# 37. Existing Implementation First

When this skill is applied to an existing Evis project:

1. Inspect the current architecture.
2. Identify what already works.
3. Identify what is partially implemented.
4. Identify what is only visual.
5. Identify what is incorrectly connected.
6. Identify hard-coded data.
7. Identify missing interfaces.
8. Identify missing behaviors.
9. Correct only the necessary parts.
10. Preserve working functionality.

Do not rebuild everything by default.

---

# 40. Desktop Application

The current web-based implementation may continue to run in a browser during development.

This is acceptable.

Do not treat browser execution as an architectural failure.

The final target is a Linux desktop application.

Desktop packaging should be implemented after the core UI/application architecture is stable.

The desktop shell should expose the same application interfaces rather than introducing a second application architecture.

---

# 41. Definition of Done

The UI should not be considered complete merely because:

* the page renders
* buttons exist
* cards exist
* menus exist
* models are displayed

The feature is complete when:

```text
UI
 ↓
real state
 ↓
correct service
 ↓
correct capability
 ↓
correct result
 ↓
correct feedback
```

For example:

### Model selector

Not complete:

```text
Ollama
LLaMA
Gemini
GPT
```

Complete:

```text
Provider detected
      ↓
Models queried
      ↓
Actual models displayed
      ↓
User selects model
      ↓
Application stores selection
      ↓
Conversation uses selected model
```

---

# 42. Guiding Principle

Evis must never pretend to have capabilities it does not actually have.

The interface should expose the architecture clearly without exposing unnecessary implementation complexity.

The user controls:

* what skill is active
* what model is used
* what provider is used
* what tools are available
* what information is persisted
* what capabilities are enabled

The system provides:

* a coherent workspace
* dynamic capability discovery
* persistent context
* modular skills
* real interaction
* local-first operation

**Build the interface around real capabilities, not around imagined capabilities.**

**Do not invent functionality to make the UI look complete.**

**Make the architecture extensible first, then connect capabilities one by one.**
